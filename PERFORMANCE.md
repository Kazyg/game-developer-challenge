# Performance report

Consolidated on 2026-10-03. These are historical measurements taken before the registration corrections; they are not a benchmark of the current changes. Raw reports, charts and profiles remain in docs/performance. The target is 60 FPS; the main run approached that callback cadence but did not prove sustained 60.00 FPS or physical presentation at 60 FPS.

## Reference environment and method

Optimized TypeScript/Vite build with sourcemaps, served by preview without HMR. Windows 10.0.26200, Intel Core i3-12100F, 17,010,458,624 bytes RAM, NVIDIA RTX 3060 driver 32.0.15.9579, headed Chromium 153.0.8010.12. Pixi WEBGL used ANGLE/NVIDIA/D3D11 with GPU composition/rasterization enabled. [Hardware evidence](docs/performance/reference-hardware.json).

Viewport/canvas 1280 × 720, DPR 1; physical display 1366 × 768 at a reported 59 Hz; balanced power mode. No CDP CPU/network throttling was requested. Thermal throttling, concurrent process load and physical presentation were not measured. Screen API values can differ from the monitor. Browser command-line defaults were not captured in these runs; the current runner records them.

Commit 5da833c518767fabaafc8123962754a7c04ac043 with pre-existing local changes; each report records git status. Seed 42, 180-second match, spawn delay 5 seconds, debug off, audio enabled at 0.45, world 4000 × 4000, configured enemy cap 43. Full configuration is in environment.game in the raw report. Real keyboard W/A/D, Space/Q/E and R inputs were generated by a navigation controller; no HP, entity or clock injection was used. Only seed entropy was controlled.

The main run did not collect CPU samples, timeline, heaps or screenshots during combat. Its screenshot was captured afterward. Browser runs were sequential, with a visible/focused tab. There were no reported pauses or JavaScript errors. Early polling could miss brief focus changes; the final runner additionally records pause/resume calls.

## Separate CPU investigation

The roughly 30-second diagnostic run is separate from the FPS baseline. [CPU profile](docs/performance/runs/2026-10-03T09-37-22-335Z/combat.cpuprofile), [source summary](docs/performance/runs/2026-10-03T09-37-22-335Z/cpu-summary.json), [timeline](docs/performance/runs/2026-10-03T09-37-22-335Z/timeline.json), [timeline summary](docs/performance/runs/2026-10-03T09-37-22-335Z/timeline-summary.json).

CollisionSystem accounted for 1.721s sampled self time: circleOverlapsPolygon 430ms, bounds 298ms and sweepCollider 251ms. World.canEnemyPose had 144,282 calls and 796ms inclusive instrumented time. Cached bounds already exist; candidate volume and repeated terrain/turn queries remain costly.

NavigationGrid.component took 205.8ms across 166 calls, concentrated in cold component construction; the largest FireAnimationFrame was 214.4ms. This does not show sustained A* overload. avoidNeighbors had 120.7ms self time and computes prediction before rejecting distant pairs. Off-camera enemies still simulate.

Rendering/HUD did not demonstrate a recurring bottleneck. The trace had 12,808 drawElements and 14,118 bindTexture calls; binds do not prove actual texture changes. WorldRenderer inclusive time was 124.7ms; its child totals must not be added again. HUD published 300 times in 16ms of measured work; those are not exact React commit counts. GPU timestamps, overdraw and VRAM were not measured.

The trace contained 331 MinorGC events (344.5ms total, max 5.034ms) and 12 MajorGC events (23.7ms total). Collision helpers allocate, but profiling and the controller also allocate: without allocation sampling by function, GC cannot be wholly attributed to hull queries. Audio generated repeated WAV requests as voice.src was reassigned; requests may use cache/ranges and do not prove repeated downloads.

## Memory after five cycles

[Measurements](docs/performance/runs/2026-10-03T10-39-47-040Z/measurements.json), [summary](docs/performance/runs/2026-10-03T10-39-47-040Z/summary.json), [chart](docs/performance/runs/2026-10-03T10-39-47-040Z/memory-chart.svg), [heap categories](docs/performance/runs/2026-10-03T10-39-47-040Z/heap-summary.json), [baseline retainers](docs/performance/runs/2026-10-03T10-39-47-040Z/warm-baseline-retainers.json), [final retainers](docs/performance/runs/2026-10-03T10-39-47-040Z/after-five-cycles-retainers.json).

After 15.02s warm-up, five start/play/pause/exit cycles completed approximately 15s each, with 5s stabilization in the menu. No unintended pauses or errors were recorded.

| Cycle | Active seconds | Sampled peak JS MiB | Menu JS MiB |
| --- | ---: | ---: | ---: |
| 1 | 15.050 | 34.29 | 10.02 |
| 2 | 15.033 | 43.91 | 29.33 |
| 3 | 15.083 | 38.11 | 25.38 |
| 4 | 15.000 | 35.97 | 33.80 |
| 5 | 15.017 | 41.88 | 29.80 |

There were zero canvases after each exit. Normal readings did not force GC per cycle and did not grow monotonically. Baseline snapshots/queryObjects can trigger GC, so this was not a completely passive sequence. Separate post-GC diagnostics grew from 8.67 to 10.90 MiB (about 2.22 MiB); final DOM/listener counts were 176/203.

| Post-GC prototype instances | Baseline | Final |
| --- | ---: | ---: |
| Game / World | 0 / 0 | 0 / 0 |
| Container / Sprite | 5 / 0 | 5 / 0 |
| Texture / Ticker | 62 / 1 | 62 / 1 |
| HTMLAudioElement | 9 | 9 |

These counts support release of observed Game/Pixi lifecycles, not unlimited stability or native/GPU cleanup. Texture count is not VRAM usage; timers/listeners were not exhaustively attributed by owner.

MessageEvent grew 276→1,057 and MessagePort 413→1,574 after GC. Strong retainer paths include ServiceWorkerContainer → listener → WorkerChannel.getWorker → ServiceWorkerSource.workerPromise → PromiseReaction → Generator → MessageEvent. An unused MSW default source waiting on a promise is a strong hypothesis, but attributing causality requires an isolated experiment. Debugger/network roots and JIT growth also contribute; not all growth is a gameplay leak.

Earlier memory runs had interrupted warm-up/cycles or retained observer arrays; they remain preserved. The final run followed observer-array release. Five 15-second cycles do not establish safety after five complete 180-second matches.

## Historical comparison and proposed follow-up

The 2026-10-02 [historical measurement](docs/performance/measurements.json) used headless Chromium/SwiftShader with GPU composition disabled, muted audio and a stationary firing player. It completed 180s, sampled 177.44s/4,992 intervals, averaged 28.15 callbacks/s with p95 50ms and peak 78 entities. Five short 5-second cycles after GC grew approximately 8.35→9.44 MiB. It is not directly comparable to the later headed GPU/controller run.

The single 20-second [calibration](docs/performance/runs/2026-10-03T10-05-10-085Z-calibration/calibration.json) measured D3D11 without observer at 59.19/s, with basic observer at 59.79/s, and forced SwiftShader at 20.80/s. This supports environmental sensitivity, not a causal optimization speedup.

Future work, not implemented by this registration correction: isolate MSW retention; reject distant neighbors before prediction; measure a spatial candidate index; investigate cold component precomputation; avoid redundant audio source changes; collect function-level allocation samples before considering pooling. Compare each change against the same seeded workload and visual quality.

## Reproduce

```sh
npm run build -- --sourcemap
npm run preview -- --host 127.0.0.1 --port 4175 --strictPort
# Another terminal, one visible/focused browser at a time:
npm run profile:reference
npm run profile:cpu
npm run profile:memory -- --seconds=15 --cycle-seconds=15
npm run profile:summarize
node scripts/summarize-heaps.mjs docs/performance/runs/<memory-run>
node scripts/inspect-retainers.mjs docs/performance/runs/<memory-run>/after-five-cycles.heapsnapshot
npm run profile:calibrate -- docs/performance/runs/<cpu-run>/measurements.json
```

PROFILE_URL changes the preview origin. PROFILE_SECONDS/PROFILE_CYCLE_SECONDS or --seconds/--cycle-seconds change collection duration. --headless is comparative. Death/pause interrupts capture without bypassing gameplay; incomplete data remains saved. complete denotes a finished 180s match; reachedRequestedDuration denotes a shorter requested window.

Runs receive UTC timestamp directories. profile:combat writes new legacy-runs rather than overwriting historical data. Full heap snapshots stay local/gitignored; summaries and retainer paths are retained. Open CPU/timeline in DevTools Performance and heaps in Memory; keep matching sourcemaps. [Instrumentation hashes](docs/performance/instrumentation-hashes.json) identify the recorded instrumentation version, not all historical source revisions.

Still unmeasured: multiple seeds, dense combat, DPR 2, larger resolutions, five complete matches, long audio/cache sessions, manual execution without CDP, physical presentation, RSS/VRAM and owner-specific timer/listener counts. No new FPS or memory claim is made for the current registration changes.
